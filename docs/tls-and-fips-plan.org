Status: design proposal for review. Nothing in this document is implemented;
it changes no code. Decisions marked =DECISION= are recommendations for the
maintainer to accept or reject.

* Scope, sources and the state of the crate

This document plans two pieces of work:

- Part A: a TLS 1.3 binding crate (=wolf-tls=) over wolfSSL's TLS layer for
  a peer channel between a fixed set of servers, driven sans-I/O through wolfSSL's I/O callbacks,
  TLS 1.3 only, one suite, one group, mutually authenticated with RFC 7250
  raw public keys pinned by SPKI hash.
- Part B: how =wolf-crypto-sys= should build against wolfSSL's validated FIPS
  140-3 module (certificate #5548, wolfCrypt v5.2.3), the known ECC
  pairwise-consistency-test blocker under =WOLFSSL_NO_MALLOC=, and which KDF is
  approved for an application's use.

** Version requirement: the vendored wolfSSL must move to 5.9.4 or later

The RPK facilities this design depends on do not exist in the vendored 5.7.2
and the 5.x RPK code had authentication-bypass bugs until 5.9.4:

- 5.9.2 (Jun 23, 2026): RPK fail-closed behaviour and the pinning API
  =wolfSSL_CTX_set_expected_rpk= / =wolfSSL_set_expected_rpk= ([CL] 5.9.2,
  "Behavioral change (Raw Public Key fail-closed)"); fix for an un-negotiated
  raw public key accepted in place of an X.509 certificate, bypassing chain
  validation ([CL] 5.9.2, "Un-negotiated Raw Public Key (RFC 7250) accepted",
  PR 10702).
- 5.9.4 (Sep 25, 2026): CVE-2026-89136, "the client side of a TLS 1.2, 1.3
  and DTLS 1.2 connection could accept an unsolicited
  =server_cert_type=RawPublicKey= which allowed a malicious or misbehaving
  server to bypass authentication ... affects versions 5.6.0 to 5.9.2" ([CL]
  5.9.4, PR 11009); "forbid sending more than one certificate with Raw Public
  Keys" (PR 11174); "fixed the verification logic for Raw Public Keys" (PR
  11458).

The TLS layer and the wolfCrypt layer must come from the same release
(=wolfssl/internal.h= is tied to the wolfCrypt headers), so =wolf-tls= forces
an update of the vendored wolfCrypt from 5.7.2 to >= 5.9.4, which means
working through =wolfcrypt-update-checklist.org= first. Two items of the
checklist are directly affected and are discussed below: the =WC_RNG= inline
DRBG (changes under static memory) and the ECC pairwise consistency test (no
longer allocates in non-=WOLFSSL_SMALL_STACK= builds on master:
=wolfcrypt/src/ecc.c:11358-11366= declares =byte sig[SIG_SZ + 32]= on the
stack and =WC_ALLOC_VAR_EX= is a no-op, =wolfssl/wolfcrypt/types.h:1064=).

** Sans-I/O design through the I/O callbacks

*** Mechanism

wolfSSL has no notion of a socket once =WOLFSSL_USER_IO= is defined
([MAN]: "WOLFSSL_USER_IO can be defined to remove the automatic setting of
the default I/O functions EmbedSend() and EmbedReceive()"). Every byte it
wants to read or write goes through the two callbacks

#+begin_src c
typedef int (*CallbackIORecv)(WOLFSSL *ssl, char *buf, int sz, void *ctx);
typedef int (*CallbackIOSend)(WOLFSSL *ssl, char *buf, int sz, void *ctx);
#+end_src

(=wolfssl/wolfio.h:820-821=). The contract, from [DOX] =wolfio.h= and
=src/internal.c= (=SendBuffered=):

- recv returns the number of bytes copied into =buf= (at most =sz=), or
  =WOLFSSL_CBIO_ERR_WANT_READ= when nothing is available; the calling
  =wolfSSL_connect/accept/read/write= then returns =-1= and
  =wolfSSL_get_error= yields =WOLFSSL_ERROR_WANT_READ=.
- send returns the number of bytes accepted (a short count is fine:
  =SendBuffered= loops, =src/internal.c:12971-13038=, =WANT_WRITE= case at 12982), or
  =WOLFSSL_CBIO_ERR_WANT_WRITE=; the unsent remainder stays in
  =ssl->buffers.outputBuffer= and is flushed at the start of the next call
  (=SendBuffered= is called before any new record is built).
- =WOLFSSL_CBIO_ERR_CONN_CLOSE= / =_CONN_RST= / =_GENERAL= are fatal.

*** The wolf-tls driving model

Each public method of a connection takes the caller's buffers for the
duration of that single call:

#+begin_src rust
pub struct Io<'a> { input: &'a [u8], consumed: usize, output: &'a mut [u8], produced: usize }
#+end_src

Immediately before every call into wolfSSL the method sets
=wolfSSL_SetIOReadCtx(ssl, &mut io)= and =wolfSSL_SetIOWriteCtx(ssl, &mut io)=
to the address of this stack-local =Io=, and the two =extern "C"= callbacks
copy out of =io.input= / into =io.output= and return =WANT_READ= /
=WANT_WRITE= when they run dry. No pointer to caller memory survives the
call: the next call installs new context pointers before wolfSSL can use the
old ones. This is the same "re-anchor before every FFI call" discipline that
=random::Rng::anchor= already uses, applied to the I/O context instead of to
a self-pointer.

The caller's loop is therefore:

1. =conn.handshake(&mut io)= -> =Status::{WantRead, WantWrite, Done}=; the
   caller ships =io.output[..produced]= to the network and feeds the next
   received bytes as =input=.
2. after =Done= the connection is =Conn<Established>=;
   =send(&mut io, plaintext) -> usize= and =recv(&mut io, plaintext_out) ->
   usize= work the same way (a record may need several calls to drain).
3. =close(&mut io)= sends =close_notify= (=wolfSSL_shutdown=, returning
   =WOLFSSL_SHUTDOWN_NOT_DONE= until the peer's =close_notify= is read,
   =wolfssl/ssl.h:3374-3378=) and yields =Conn<Closed>=.

wolfSSL itself never blocks and never sleeps in this configuration; the only
system interaction left in the TLS layer is the DRBG seed (section
[[*Entropy][Entropy]]).

*** Memory: per-connection static pools

The TLS layer is not allocation-free: =wolfSSL_CTX_new_ex= and =wolfSSL_new=
allocate the =WOLFSSL_CTX= (280 bytes) and =WOLFSSL= (1216 bytes) objects,
the handshake allocates the =DecodedCert= (3688 bytes), the ECC keys, the
handshake hashes and the record buffers ([MEAS], sizes under the profile of
Appendix A). Under =WOLFSSL_NO_MALLOC= alone every one of these fails. wolfSSL's
answer is =WOLFSSL_STATIC_MEMORY= ([DOX] =memory.h=, =wc_LoadStaticMemory=;
=configure.ac:12136-12180=, =--enable-staticmemory=): the caller hands over a
buffer which =wc_LoadStaticMemory= partitions into fixed buckets
(=WOLFMEM_BUCKETS= / =WOLFMEM_DIST=, =wolfssl/wolfcrypt/memory.h:104-200=),
=XMALLOC(size, heap, type)= becomes =wolfSSL_Malloc(size, heap, type)=
(=wolfssl/wolfcrypt/types.h:890-905=), and with =WOLFSSL_NO_MALLOC= also
defined there is no fallback to =malloc= when no heap hint is present
(=wolfcrypt/src/memory.c:1052-1083=: "No heap hint found to use and no
malloc").

For TLS the pool is attached to the context:

#+begin_src c
wolfSSL_CTX_load_static_memory(&ctx, wolfTLSv1_3_server_method_ex, gen, genSz,
                               WOLFMEM_GENERAL | WOLFMEM_TRACK_STATS, 1);
wolfSSL_CTX_load_static_memory(&ctx, NULL, io, ioSz,
                               WOLFMEM_IO_POOL_FIXED | WOLFMEM_TRACK_STATS, 1);
#+end_src

(=src/ssl.c:1486-1523=, [DOX] =ssl.h= =wolfSSL_CTX_load_static_memory=). The
first call creates the =WOLFSSL_CTX= /inside/ the general pool; the second
dedicates two fixed =WOLFMEM_IO_SZ= (16992-byte) blocks per connection to the
record input and output buffers, so a 16 KiB record never triggers a bucket
search. =WOLFMEM_TRACK_STATS= makes =wolfSSL_is_static_memory= /
=wolfSSL_CTX_is_static_memory= report peak and current usage.

Measured on the Appendix A profile ([MEAS], one mutual-RPK handshake plus one
application record each way, =-Os=):

| Quantity                                         | Client     | Server     |
|--------------------------------------------------+------------+------------|
| general-pool peak (bucket granularity)           | 27,424 B   | 27,616 B   |
| general-pool peak live blocks                    | 21         | 24         |
| allocations / frees over the connection          | 39 / 34    | 46 / 41    |
| fixed IO blocks                                  | 2 x 16,992 | 2 x 16,992 |
| handshake bytes on the wire (sent)               | 492        | 534        |

A wrapped =malloc= that aborts proved that no libc allocation happens
after =wolfSSL_Init()= with this profile ([MEAS], =-Wl,--wrap=malloc=).

A per-connection budget of 64 KiB general pool (the measured 28 KiB peak
plus bucket overhead and headroom for the X.509 fallback, whose
=DecodedCert= is the same 3688 bytes but whose certificate is larger than a
91-byte SPKI) and 2 x 17 KiB fixed IO blocks, i.e. about 100 KiB per peer
connection, is the planning number. The exact bucket list should be
re-measured on the final profile with =WOLFMEM_TRACK_STATS= as
=examples/configs/user_settings_tinytls13.h= does for its own profile
(comment "Static-memory pool buckets ... measured with").

*** Entropy

=wolfSSL_new= instantiates a Hash-DRBG for the connection
(=ReinitSSL= -> =wc_InitRng_ex=). With =NO_FILESYSTEM= and no =getrandom=
the default seed function has no source left and =wc_GenerateSeed= fails
with =NOT_COMPILED_IN= (=-174=) ([MEAS]; =wolfcrypt/src/random.c:11856-12030=:
the =/dev/urandom= path is under =#ifndef NO_FILESYSTEM=, the =getrandom=
path under =HAVE_GETRANDOM=). =wolf-tls= must therefore choose explicitly:

- =DECISION= (recommended): =WC_RNG_SEED_CB= and =wc_SetSeed_Cb=
  (=wolfssl/wolfcrypt/random.h=, [VEN] line 244-245 and master) with a seed
  callback supplied by the Rust side, so the crate stays independent of the
  OS and the same mechanism satisfies the FIPS policy, which requires the
  application to "register an entropy callback to load entropy into the
  module from an external entropy source" ([SP] 11.1, p. 50).
- On hosted Linux targets =HAVE_GETRANDOM= is an acceptable alternative
  (used for the measurements).

*** Threading

A =Conn= is driven by one thread at a time (=&mut self=); its pools are its
own. wolfSSL's remaining process-wide state in this profile is
=wolfSSL_Init()= (reference counted; call once from a Rust =Once=) and the
per-pool mutex (=WOLFSSL_HEAP::memory_mutex=, absent under
=SINGLE_THREADED=, =wolfssl/wolfcrypt/memory.h:264-266= (=memory_mutex=, line 265)). With one pool per
connection the pool mutex is redundant and =SINGLE_THREADED= is sound /only
if no pool is ever shared between threads/; the FIPS path below wants a
shared pool, so the recommendation is to keep wolfSSL's mutex compiled in
(on =no_std= targets through =WOLFSSL_USER_MUTEX= implemented in Rust) and
let =Conn= be =Send + !Sync=.

** The safe Rust API

*** Shape

#+begin_src rust
// wolf-tls
pub struct Spki(pub [u8; 91]);                   // DER SubjectPublicKeyInfo, P-256, uncompressed
pub struct SpkiHash(pub [u8; 32]);               // SHA-256 of the DER SPKI (what wolfSSL stores)

pub struct Identity { key: wolf_crypto::ecc::PrivateKey<P256>, spki: Spki }   // our credential
pub struct Pins<const N: usize> { spki: [Spki; N] }                           // peers we accept

pub struct Pool<const GENERAL: usize, const IO: usize> { /* [u8; GENERAL], [u8; IO] in a Zeroizing wrapper */ }

Notes on the typestate:

- =Conn<Handshaking>= has no =send= / =recv=; =Conn<Closed>= has nothing
  but =Drop=. Misuse does not compile.
- =established()= is the only way to obtain =Conn<Established>= and it checks
  =wolfSSL_is_init_finished= (=wolfssl/ssl.h:3246=; returning =Err(self)= otherwise), so a
  connection cannot be promoted by the caller's bookkeeping alone.
- The =WOLFSSL= and =WOLFSSL_CTX= live inside the borrowed pool, so the
  =Conn= value itself is freely movable (it holds raw pointers into memory it
  does not own and that cannot move while the borrow lasts). The pool borrow
  is exclusive for the life of the connection; the pool is reusable after
  the =Conn= is dropped and zeroized.
- One =WOLFSSL_CTX= per connection (not shared): a context carries the
  credential, pins and pool, all per peer in the application's model; sharing would
  need the pool mutex and brings nothing.
- =Error= is a small enum (section [[*Error mapping][Error mapping]]), never a wolfSSL integer.

*** Peer identity

Two mechanisms, used together:

1. /Authorization/ is wolfSSL's: the handshake can only complete if the peer's
   RPK matches one of the pins (=RpkIsTrusted=, =src/internal.c:18623=, applied at 19733-19777).
2. /Identification/ is the crate's: the verify callback (always invoked for
   the leaf thanks to =WOLFSSL_ALWAYS_VERIFY_CB=) receives
   =store->certs[0]= which, for an RPK peer, is the DER SPKI exactly as
   received (=src/internal.c:16751-16752=; the same bytes
   =wolfSSL_CTX_set_expected_rpk= hashes). The callback, with the =Conn= as
   =userCtx= via =wolfSSL_SetCertCbCtx=, hashes it with
   =wolf_crypto::hash::Sha256=, checks it against the pin set again (defence
   in depth; an RPK peer that is not pinned is rejected by returning 0 even if
   wolfSSL's own check were ever bypassed), and stores the =SpkiHash= in
   =Conn::peer=. =Conn<Established>::peer()= returns a =PeerIdentity { hash:
   SpkiHash, spki: Spki, key: PublicKey<P256> }= where =key= is produced
   through =PublicKey::<P256>::from_spki_der=, i.e. with full public-key
   validation by =wolf-crypto=.

If the X.509 fallback is enabled the same callback compares the whole DER
leaf in =store->certs[0]= with the pinned leaves and ignores =preverify=
(which will report =ASN_NO_SIGNER_E= for a self-signed leaf with no CA
loaded); the peer identity is then the SHA-256 of the SPKI extracted from the
pinned leaf. The fallback is a configuration-time choice (=Pins= of
certificates instead of SPKIs), not a runtime negotiation: a peer that
offers X.509 when RPK is configured is refused by wolfSSL because the
offered certificate type is not in the negotiated list (5.9.2/5.9.4 fixes
above).

*** Zeroization

- wolfSSL zeroizes its own key material on =wolfSSL_free= (=FreeSSL= ->
  =FreeArrays= / =ForceZero= of secrets; the input buffer is =ForceZero='d
  when encryption was on, =src/ssl.c:5993=).
- The crate does not rely on that alone: =Pool= is =Zeroizing=-wrapped and
  =Conn::drop= zeroizes the entire general and IO pools after
  =wolfSSL_free= / =wolfSSL_CTX_free=. Everything the connection ever
  allocated, including anything wolfSSL forgot, is thereby erased; this is a
  property only the per-connection-pool design can give.
- =Identity= holds a =wolf_crypto::ecc::PrivateKey= (zeroized on drop) and
  exports it into wolfSSL as DER only for the =wolfSSL_CTX_use_PrivateKey_buffer=
  call, from a =Zeroizing<[u8; 121]>= stack buffer; wolfSSL keeps its own
  copy inside the pool (zeroized with the pool).
- Plaintext handed to =send= is copied by wolfSSL into the output buffer
  (pool) and encrypted in place; =recv= decrypts in the fixed input buffer
  (pool) and copies out. Both are inside the zeroized pool.

** Proposed =fips= build path for wolf-crypto-sys

=DECISION= (recommended):

1. The module is built by wolfSSL's own procedure, not by =cc=. A =fips=
   feature of =wolf-crypto-sys= disables the vendored compilation and instead
   reads =WOLF_CRYPTO_FIPS_DIR= (install prefix of a bundle built per the
   UG: =./configure --enable-fips=v5 ...= with the UG's flag set, or the
   =user_settings.h= method of policy 11.1) and links =libwolfssl=
   (shared, see 3). The build script fails if the directory, =wolfssl/options.h=
   (or the user-settings header) or =fips_test.h= is missing, and refuses to
   proceed if =HAVE_FIPS= / =HAVE_FIPS_VERSION= in =options.h= do not say
   v5.2.3 - the crate must never silently bind a non-validated library under
   the =fips= feature.
2. bindgen runs against the bundle's headers with =options.h= first (policy
   11.1), so the =_fips= wrapper symbols are what the bindings call. The
   Rust side does not hard-code symbol names: =wolf-crypto= calls
   =wolf_crypto_sys::wc_ecc_make_key_ex= and the =fips= feature maps that to
   the wrapper (a =cfg(feature = "fips")= re-export layer in the sys crate,
   generated from the bundle's =fips.h=; its exact spelling is open question
   B-1).
3. Link the module dynamically by default under =fips=. A shared
   =libwolfssl.so= built and hashed by the UG procedure carries its own,
   stable in-core hash and is the deployment unit the policy describes
   ("Updates to the Module are provided as a complete replacement", 2.1,
   p. 7). Static linking is offered as =fips-static=, documented as
   requiring the =fips-hash-offline.sh= post-link step on the final application
   executable, and is not the default because Cargo has no post-link hook.
4. Runtime API in =wolf-crypto= (=cfg(feature = "fips")=, module =fips=):
   #+begin_src rust

** The ECC pairwise-consistency-test blocker

*** Analysis

Under FIPS v5+ (or =WOLFSSL_VALIDATE_ECC_KEYGEN=), =wc_ecc_make_key_ex=
ends with =_ecc_pairwise_consistency_test(key, rng)= (=ecc.c= [VEN]
6039-6050; master 6408-6419), which signs and verifies a random digest. In
the vendored 5.7.2 the signature buffer is allocated with
=XMALLOC(sigLen + digestLen, NULL, DYNAMIC_TYPE_ECC)= - note the =NULL= heap
([VEN] =ecc.c:10229=) - so under =WOLFSSL_NO_MALLOC= it returns
=MEMORY_E= and key generation fails. On master the buffer is on the stack
unless =WOLFSSL_SMALL_STACK= is defined, and when it is allocated the heap is
=key->heap= (=ecc.c:11358-11366=). Which of the two the validated v5.2.3
=ecc.c= contains is not visible from outside the bundle (open question B-2).
The =fips.c= wrappers also allocate nothing of their own that we know of,
but the same uncertainty applies.

=memory.c= and =types.h= are /outside/ the boundary (Table 3), so the memory
plumbing can be changed without touching validated code; the =XMALLOC=
macro, however, is expanded /inside/ the boundary files, so the memory
option chosen must be one the UG allows for the module build (policy 6.2).

*** The static-memory decision

=DECISION= (recommended): adopt =WOLFSSL_STATIC_MEMORY= together with
=WOLFSSL_NO_MALLOC= as the crate's single memory model (option 1), because:

- =wolf-tls= needs it anyway: the TLS layer cannot run without an allocator,
  and per-connection pools with fixed IO blocks give deterministic,
  isolated, zeroizable memory per peer (Part A). One model for the whole
  stack is simpler to reason about and to audit than "no-malloc for
  wolfCrypt, pools for TLS, a callback arena for FIPS".
- It resolves the PCT blocker for /both/ possible shapes of the validated
  =ecc.c= (global hint for the =NULL=-heap shape, =key->heap= for the other).
- It is wolfSSL's designed, documented and =configure=-exposed mechanism
  (=--enable-staticmemory=), hence the most likely of the options to appear
  on the UG's allowed list; option 2's =wolfSSL_SetAllocators= is equally
  outside the boundary but relies on =WOLFSSL_NO_MALLOC= semantics in
  =memory.c= that wolfSSL has evidently not exercised with the FIPS PCT.
- The measured cost is small (section [[*Memory: per-connection static pools][Memory: per-connection static pools]]; 2-3 pool blocks for
  all of ECC).

Consequences for =wolf-crypto= (to be done when the vendored sources move
to 5.9.4, before =wolf-tls=):

- =random::Rng= stops being self-referential (=drbg_data= no longer exists
  under static memory, so =Rng::anchor= must go behind
  =cfg(not(feature = "static-memory"))= or simply be removed with the
  feature always on). =Rng::new()= needs a heap: either =Rng::new_in(&Heap)=
  with =wc_InitRng_ex(rng, heap, INVALID_DEVID)=, or =Rng::new()= using the
  crate-global heap. The DRBG state then lives in the pool, which must
  outlive the =Rng= - a lifetime on =Rng<'h>= expresses this.
- =ecc::Key= keeps its "no pointers into itself" invariant: =heap= points at
  the caller's =WOLFSSL_HEAP_HINT=, outside the key. =Key::copy= remains
  sound. The checklist entry gains "=heap= is the pool hint, which outlives
  every key created from it".
- A =Heap= type wraps =WOLFSSL_HEAP_HINT= over a caller-owned
  =Zeroizing<[u8; N]>= (=wc_LoadStaticMemory_ex= with a crate-chosen bucket
  list sized from the measurements: for wolfCrypt alone a few 1 KiB blocks
  suffice; for TLS the per-connection pools of Part A). A crate-global
  =Heap= (=static= pool behind a =Once=) is registered with
  =wolfSSL_SetGlobalHeapHint= at =fips::init= / first use so that
  boundary code allocating with a =NULL= heap lands in it. Because that
  pool is shared between threads, wolfSSL's pool mutex stays compiled in
  (no =SINGLE_THREADED=; =WOLFSSL_USER_MUTEX= on =no_std=).
- Hashes, HMAC, AES, AES-GCM, ChaCha, Poly1305, HKDF and PBKDF2 do not
  allocate in this configuration (no =WOLFSSL_SMALL_STACK=), so their
  constructors keep passing a =NULL= heap and their API is unchanged.
- Fallback if the UG forbids =WOLFSSL_STATIC_MEMORY= but allows
  =WOLFSSL_NO_MALLOC=: option 2 (allocator callback into a Rust arena) for the
  wolfCrypt-only FIPS build; it is a day's work and leaves the TLS build on
  option 1 in non-FIPS mode. If the UG forbids =WOLFSSL_NO_MALLOC= as well,
  the FIPS build must use the bundle as shipped (libc =malloc= inside the
  module), and the crate's "no-alloc" guarantee then stops at the FFI
  boundary for the =fips= feature; this must be stated in the docs rather
  than papered over.

** Which KDF is approved, and what it means for =kdf::hkdf=

Table 7 of [SP] lists, as the only key-derivation functions: =KDF SSH
(CVL)=, =KDF TLS (CVL)= v1.2, =TLS v1.2 KDF RFC7627 (CVL)= and =TLS v1.3 KDF
(CVL)=, all under SP 800-135 rev. 1, and Table 10 adds for the KAS-SSC with
KDF entry: "Key derivation: Per IG 2.4.B resolution 6 and 7 All KDF's shall
only be used within their respective protocols." There is no SP 800-56C
rev. 2 one-/two-step KDF (that is what RFC 5869 HKDF would be approved as),
no SP 800-108 KBKDF, and no SP 800-132 PBKDF2. 2.11 (p. 25) adds the IG D.C
statement that "No parts of the TLS protocol other than the approved
cryptographic algorithms and the KDFs, have been tested".

Consequences:

- The TLS 1.3 key schedule run by wolfSSL's TLS layer (HKDF-Extract /
  HKDF-Expand-Label through =wc_Tls13_HKDF_Extract_ex= /
  =wc_Tls13_HKDF_Expand_Label_ex= in =kdf.c=, =wolfssl/wolfcrypt/kdf.h:88-110=,
  a boundary file) with SHA-384 is an approved use of the module
  (=FIPS_CAST_KDF_TLS13=). =wolf-tls= over a FIPS build is therefore an
  approved consumer, and every peer-channel key an application derives /inside the
  TLS handshake/ is approved keying material (=KD_DKM=, Table 18).
- Stand-alone HKDF (=wc_HKDF= in =hmac.c=, =wolfssl/wolfcrypt/hmac.h:210-224=)
  is not an approved service of #5548, so the crate's =kdf::hkdf= is
  correctly behind =allow-non-fips= and must stay there. An application must not
  derive keys from an ECDH =SharedSecret= with HKDF and call that approved;
  the approved way to turn a P-256 agreement into keys with this module is
  the TLS 1.3 handshake itself. If an application needs an approved stand-alone KDF
  (for example for data-at-rest keys), it has to wait for a wolfCrypt
  module whose certificate lists an SP 800-56C or SP 800-108 KDF; the CAST
  identifier list in [WS] =fips_test.h= (through v7.0.0) contains no HKDF or
  KBKDF CAST, so no current or announced wolfCrypt module provides one
  (open question B-4).
- The same table shows that PBKDF2 is /not/ approved under #5548
  (=FIPS_CAST_PBKDF2= first appears with v6.0.0 in =fips_test.h=). The
  crate currently exposes =kdf::FipsPbkdf2= as a =Fips= type; against
  certificate #5548 that marker is not justified. This document does not
  change it; it is flagged for the maintainer.
- AES-GCM in the crate is approved only with the IV rules of policy 2.7.3.a:
  internal IV generation from the module's DRBG with a nonce of
  >= 96 bits, or protocol (TLS) external IVs. The crate's =aead::AesGcm=
  API, which takes a caller-supplied IV, is the "external IV" case and is
  only approved when the IV comes from the TLS KDF; for an application's own
  at-rest encryption the API would need an =encrypt_with_internal_iv=
  variant (=wc_AesGcmSetIV= / =wc_AesGcmEncrypt_ex=, =wolfssl/wolfcrypt/aes.h:787-790=). Out of scope here,
  noted because it falls out of the same table.

#+begin_src c
struct pipe { unsigned char buf[1 << 16]; size_t len; };
struct endpoint { struct pipe* rx; struct pipe* tx; int bytes_in, bytes_out; };

static int cb_recv(WOLFSSL* ssl, char* buf, int sz, void* ctx) {
    struct endpoint* ep = ctx; size_t n;
    if (ep->rx->len == 0) return WOLFSSL_CBIO_ERR_WANT_READ;
    n = (size_t)sz < ep->rx->len ? (size_t)sz : ep->rx->len;
    memcpy(buf, ep->rx->buf, n); memmove(ep->rx->buf, ep->rx->buf + n, ep->rx->len - n);
    ep->rx->len -= n; ep->bytes_in += (int)n; return (int)n;
}
static int cb_send(WOLFSSL* ssl, char* buf, int sz, void* ctx) {
    struct endpoint* ep = ctx;
    if (ep->tx->len + (size_t)sz > sizeof(ep->tx->buf)) return WOLFSSL_CBIO_ERR_GENERAL;
    memcpy(ep->tx->buf + ep->tx->len, buf, (size_t)sz); ep->tx->len += (size_t)sz;
    ep->bytes_out += sz; return sz;
}

#define GEN_SZ (160 * 1024)            /* generous for measuring; 64 KiB is the budget */
#define IO_SZ  (2 * WOLFMEM_IO_SZ + 1024)
struct side { unsigned char gen[GEN_SZ], io[IO_SZ]; WOLFSSL_CTX* ctx; WOLFSSL* ssl; struct endpoint ep; };

static int setup(struct side* s, int server, const byte* spki, size_t spkiSz,
                 const byte* key, size_t keySz, const byte* peer, size_t peerSz, int load_cred) {
    int groups[1] = { WOLFSSL_ECC_SECP256R1 }; char rpk[1] = { WOLFSSL_CERT_TYPE_RPK };
    s->ctx = NULL;
    if (wolfSSL_CTX_load_static_memory(&s->ctx, server ? wolfTLSv1_3_server_method_ex
            : wolfTLSv1_3_client_method_ex, s->gen, GEN_SZ, WOLFMEM_GENERAL | WOLFMEM_TRACK_STATS, 1)
            != WOLFSSL_SUCCESS) return -1;
    if (wolfSSL_CTX_load_static_memory(&s->ctx, NULL, s->io, IO_SZ,
            WOLFMEM_IO_POOL_FIXED | WOLFMEM_TRACK_STATS, 1) != WOLFSSL_SUCCESS) return -1;
    wolfSSL_CTX_SetIORecv(s->ctx, cb_recv); wolfSSL_CTX_SetIOSend(s->ctx, cb_send);
    wolfSSL_CTX_set_verify(s->ctx, WOLFSSL_VERIFY_PEER | WOLFSSL_VERIFY_FAIL_IF_NO_PEER_CERT, NULL);
    if (wolfSSL_CTX_set_cipher_list(s->ctx, "TLS13-AES256-GCM-SHA384") != WOLFSSL_SUCCESS) return -2;
    if (wolfSSL_CTX_set_groups(s->ctx, groups, 1) != WOLFSSL_SUCCESS) return -3;
    if (wolfSSL_CTX_set_client_cert_type(s->ctx, rpk, 1) != WOLFSSL_SUCCESS) return -4;
    if (wolfSSL_CTX_set_server_cert_type(s->ctx, rpk, 1) != WOLFSSL_SUCCESS) return -5;
    if (load_cred) {
        if (wolfSSL_CTX_use_certificate_buffer(s->ctx, spki, (long)spkiSz, WOLFSSL_FILETYPE_ASN1) != WOLFSSL_SUCCESS) return -6;
        if (wolfSSL_CTX_use_PrivateKey_buffer(s->ctx, key, (long)keySz, WOLFSSL_FILETYPE_ASN1) != WOLFSSL_SUCCESS) return -7;
    }
    if (peer && wolfSSL_CTX_set_expected_rpk(s->ctx, peer, (unsigned)peerSz) != WOLFSSL_SUCCESS) return -8;
    if ((s->ssl = wolfSSL_new(s->ctx)) == NULL) return -9;
    wolfSSL_SetIOReadCtx(s->ssl, &s->ep); wolfSSL_SetIOWriteCtx(s->ssl, &s->ep);
    return 0;
}

static int drive(struct side* c, struct side* s, int* err_c, int* err_s) {
    int i, done_c = 0, done_s = 0; *err_c = *err_s = 0;
    for (i = 0; i < 40 && !(done_c && done_s); i++) {
        if (!done_c) { int r = wolfSSL_connect(c->ssl); if (r == WOLFSSL_SUCCESS) done_c = 1;
            else { int e = wolfSSL_get_error(c->ssl, r);
                   if (e != WOLFSSL_ERROR_WANT_READ && e != WOLFSSL_ERROR_WANT_WRITE) { *err_c = e; return -1; } } }
        if (!done_s) { int r = wolfSSL_accept(s->ssl); if (r == WOLFSSL_SUCCESS) done_s = 1;
            else { int e = wolfSSL_get_error(s->ssl, r);
                   if (e != WOLFSSL_ERROR_WANT_READ && e != WOLFSSL_ERROR_WANT_WRITE) { *err_s = e; return -1; } } }
    }
    return (done_c && done_s) ? 0 : -2;
}
