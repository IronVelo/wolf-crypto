#+TITLE: Update Checklist for Underlying =wolfcrypt=
#+OPTIONS: toc:2 num:t author:nil

* Introduction

This document goes over what needs to be ensured prior to updating to a new version
of =wolfcrypt=. This library makes assumptions based on the current state of =wolfcrypt=,
these assumptions are made via reviewing the source code of =wolfcrypt=, rather than things
protected by semantic versioning. Prior to updating the underlying =wolfcrypt= library,
these assumptions must be audited, ensuring that no changes in =wolfcrypt= violate them.

This also means, that under =wolfcrypt= updates this library does not necessarily follow
the same versioning scheme as =wolfcrypt=. While =wolfcrypt= may introduce changes—such as
mutating a pointer that was previously unmodified—without it being considered a breaking
change (since the pointer is not declared as =const=), this would have significant consequences
for our API. Specifically, in our Rust API, we rely on the assumption that certain functions,
such as those related to cryptographic hashing, do not mutate their =src= pointer, even though
=wolfcrypt= does not enforce this immutability at the API level.

For instance, we implement =Clone= for certain cryptographic hashers by internally calling
=wolfcrypt='s =Copy= functions, which take a mutable pointer but do not currently mutate
the =src= data. If =wolfcrypt= were to start mutating the =src= pointer in these functions,
it would force a breaking change in our Rust API, as we would have to remove the =Clone=
implementation or move it to a method that takes a mutable reference. Therefore, what may be a
non-breaking change for =wolfcrypt= could be a breaking change for us, and we must audit each
new version of =wolfcrypt= carefully to ensure our assumptions still hold.

In short, a =patch= version update in =wolfcrypt= could result in a =minor= or even =major=
version update for our Rust API, depending on whether it impacts these assumptions.

The assumptions we make are not very out there, they undergo ridicule, and include arguments
for why they are valid.

* Checklist

Right now, since we make minimal assumptions, there are only a few things to ensure on each update.
If we are forced to continue making assumptions this list will expand. On every update of
=wolfcrypt= we will need to check every item of this checklist prior to updating our Rust API.

- Ensure that =wolfcrypt='s =Copy= functions for hashing algorithms do not mutate the =src=
  pointer. The =Copy= functions' =src= pointer is not declared as =const=, therefore they can
  begin mutating the =src= pointer (unlikely) without introducing any breaking changes.

  We will need to check all places in which we depend on this current state remaining true,
  these are:

  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha256.c#L2527][sha256]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha256.c#L2391][sha224]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha512.c#L2155][sha384]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha512.c#L1870][sha512]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha3.c#L974][sha3 family (including SHAKE)]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/sha.c#L1117][sha1]]
  - [[https://github.com/wolfSSL/wolfssl/blob/master/wolfcrypt/src/md5.c#L541][MD5 (MD4 etc does not have a Copy impl)]]

  Blake2 does not include a Copy impl.

- Ensure that, under =WOLFSSL_NO_MALLOC= (and without =WOLFSSL_STATIC_MEMORY=), =WC_RNG= still
  stores its DRBG state inline in =WC_RNG::drbg_data= and that =WC_RNG::drbg= only ever points at
  that field (or is null). =_InitRng= sets =rng->drbg = &rng->drbg_data= ([[file:wolf-crypto-sys/wolfcrypt/src/wolfcrypt/src/random.c][random.c]],
  =_InitRng=), which makes the =WC_RNG= self-referential, and Rust moves values freely. =random::Rng=
  therefore re-points =drbg= at its own =drbg_data= before every call into wolfcrypt (=Rng::anchor=,
  used by =Rng::as_mut_ptr= and =Drop=). Without this, a moved =Rng= makes wolfcrypt read and write
  (and on free, zero) the memory where the =Rng= was first initialized.

  Check that:
  - =drbg= is only assigned in =_InitRng= (to =&rng->drbg_data= or null on failure) and in
    =wc_FreeRng= (null), and that no other pointer into the =WC_RNG= is stored anywhere;
  - the field names =drbg= and =drbg_data= are unchanged (otherwise the build fails, which is fine).

- Ensure that =ecc_key= (and =ecc_point=, =mp_int= / =fp_int=) remain plain data under our
  configuration: no pointers into the key itself and no owned allocations. =ecc::Key= is moved by
  Rust, and bitwise copied (=Key::copy=) to call functions which take a non-const =ecc_key*= from a
  shared reference: =wc_ecc_verify_hash= (writes =key->state=), =wc_ecc_export_x963=,
  =wc_ecc_export_private_only=, =wc_EccPublicKeyToDer=, and the peer key of
  =wc_ecc_shared_secret=. The copies are zeroed on drop.

  The current struct only holds =dp= (pointer to the static =ecc_sets= table), =heap= (null),
  =rng= (see below) and inline big integers. Any of these defines would break the assumption and
  must not be enabled without revisiting =ecc::Key=: =ALT_ECC_SIZE= (=ecc_point= points into
  itself), =WOLFSSL_SMALL_STACK_CACHE= (=t1=, =t2=, =pubkey.key= back-pointer),
  =WOLFSSL_ECDSA_SET_K= / =WOLFSSL_ECDSA_DETERMINISTIC_K= without =WOLFSSL_NO_MALLOC= (heap
  =sign_k=), =WOLFSSL_ASYNC_CRYPT=, =WC_ECC_NONBLOCK=, =WOLF_CRYPTO_CB= and the hardware back-ends
  (device contexts and handles), =WOLFSSL_CUSTOM_CURVES= (=deallocSet=, allocated curve parameters).

- Ensure that the =rng= stored by =wc_ecc_set_rng= is only used by the calls made while it is set.
  =PrivateKey::diffie_hellman= sets it to the caller's (mutably borrowed) =Rng= for one
  =wc_ecc_shared_secret= call and resets it to null afterwards. Check that no other function we call
  on a private key dereferences =key->rng= (currently: =wc_ecc_shared_secret_gen_sync= requires it
  under =ECC_TIMING_RESISTANT=; =ecc_check_privkey_gen= and =ecc_blind_k_rng= use it when set, but
  are not compiled in our configuration; signing, key generation and =wc_ecc_make_pub_ex= take
  the rng as an argument).

- Ensure that =wc_ecc_shared_secret= still does not need its own validation of the peer key.
  It does not validate the public point; we rely on =ecc::PublicKey= only being constructible
  through =wc_ecc_check_key= (full validation, SP 800-56A rev. 3 5.6.2.3.3, which requires
  =HAVE_ECC_CHECK_PUBKEY_ORDER=, defined in =ecc.c= for software fast math builds), or from a
  validated =PrivateKey=. Check that =wc_ecc_check_key= still performs the infinity, range,
  on-curve and order checks, and the private key range check =[1, n - 1]= for private keys.

- Ensure that =wc_EccPublicKeyDecode= only accepts named curves in our build (no
  =WOLFSSL_CUSTOM_CURVES=) and still reports the consumed length through =inOutIdx=. We require the
  whole input to be consumed and the curve (=wc_ecc_get_curve_id(key->idx)=, reading the public
  =idx= field) to be the expected one. =wc_ecc_sig_to_rs= may accept non-canonical encodings,
  =ecc::Signature::from_der= re-encodes and compares, so this does not need to hold.

- Key generation self-tests. =WOLFSSL_VALIDATE_ECC_KEYGEN= (and FIPS v5+, which forces it) runs
  =_ecc_pairwise_consistency_test= after =wc_ecc_make_key_ex=, which allocates its signature buffer
  with =XMALLOC= and therefore always fails with =MEMORY_E= under =WOLFSSL_NO_MALLOC=. We do not
  define it; =PrivateKey::generate= instead runs =wc_ecc_check_key= on the new key. A FIPS bundle
  build with =WOLFSSL_NO_MALLOC= needs this resolved (static memory or a wolfSSL change) before ECC
  key generation can work there. Check on update whether the pairwise test still allocates.

The ECC and RNG items above were checked against the vendored sources on 2026-10-20.

- Ensure that the AES key wrap functions (=HAVE_AES_KEYWRAP=, [[file:wolf-crypto-sys/wolfcrypt/src/wolfcrypt/src/aes.c][aes.c]]) keep the contract
  =aes::kw= relies on:
  - =wc_AesKeyWrap_ex= writes exactly =inSz + 8= bytes of =out= and returns =inSz + 8=;
    =wc_AesKeyUnWrap_ex= writes exactly =inSz - 8= bytes and returns =inSz - 8=, or
    =BAD_KEYWRAP_IV_E= when the integrity check value does not match. A null =iv= selects the
    default ICV (=0xA6= * 8) in both.
  - On an integrity failure =wc_AesKeyUnWrap_ex= has already written the unauthenticated plaintext
    to =out=. =Kek::unwrap= zeroes its output buffer on every error; check that the function still
    never writes outside =out[..inSz - 8]=.
  - =wc_AesFree= does not clear the key schedule in our configuration, =aes::kw= therefore keeps the
    =Aes= on its own frame and zeroes it after =wc_AesFree= (=with_schedule=). If =wc_AesFree= starts
    owning resources (e.g. =WOLFSSL_AESGCM_STREAM= with =WOLFSSL_SMALL_STACK=, device back-ends),
    zeroing after it is still correct, but =Aes= must remain plain data for =zeroize_flat_type=.
  - Known weaknesses of the current implementation, to recheck on update: the ICV comparison in
    =wc_AesKeyUnWrap_ex= is =XMEMCMP= (not constant time), and its stack temporary =tmp= keeps the
    first recovered plaintext semiblock after return (it is not cleared). Neither can be fixed
    without reimplementing the mode; prefer a =wolfcrypt= version which uses =ConstantCompare= and
    =ForceZero= if one becomes available.
  - KWP (SP 800-38F section 6.3, RFC 5649) is not implemented by the vendored =wolfcrypt=. If an
    update adds it, it can be exposed alongside KW.
  - =WOLFSSL_AES_DIRECT= and =HAVE_AES_KEYWRAP= do not change the layout of =struct Aes= (bindgen
    and the C build both define them, but this must stay true for any define only given to one).

The AES key wrap items above were checked against the vendored sources on 2026-10-20.

- Ensure that =random::Rng= is still a Hash_DRBG, which its =Fips= marker relies on. This holds while
  =HAVE_HASHDRBG= is the generator: =CUSTOM_RAND_GENERATE_BLOCK=, =WC_NO_HASHDRBG= or
  =HAVE_INTEL_RDRAND= (which bypasses the DRBG in =_InitRng= and =wc_RNG_GenerateBlock=, and makes
  =wc_RNG_DRBG_Reseed= a successful no-op) must not be enabled without revisiting the marker and
  =Rng::reseed=.

- Ensure that the DRBG functions behind =random::hash_drbg= and =random::kat= keep their contract
  ([[file:wolf-crypto-sys/wolfcrypt/src/wolfcrypt/src/random.c][random.c]]):
  - =wc_InitRngNonce= only reads the nonce (the parameter is not =const=) and passes it to
    =Hash_DRBG_Instantiate= as the nonce. With a caller nonce it draws =SEED_SZ= entropy bytes and no
    nonce of its own (=SEED_SZ + SEED_SZ / 2= without), so =Rng::with_nonce= requires at least 16 bytes.
  - =wc_RNG_DRBG_Reseed= does not check the entropy length nor the generator status, and returns 0
    (=DRBG_SUCCESS=) or a non-zero error. =Rng::reseed= enforces at least 32 bytes and runs
    =wc_RNG_TestSeed= first; check that =wc_RNG_TestSeed= still only reads =seedSz= bytes and needs
    =seedSz > SEED_BLOCK_SZ=.
  - =wc_RNG_HealthTest_ex= instantiates (entropy A, nonce), optionally reseeds (entropy B), generates
    twice and returns the second block, requires =outputSz == RNG_HEALTH_TEST_CHECK_SIZE= (128) and
    uninstantiates its DRBG on every path. It takes no personalization string nor additional input,
    which limits =random::kat= (and the CAVP sections tested) accordingly.
  - =WC_RNG_SEED_CB= is not defined. Its seed callback is process global (=wc_SetSeed_Cb=), so it is
    not exposed; enabling it changes the entropy source of every =Rng=.

The DRBG items above were checked against the vendored sources on 2026-10-20.

* External Device Offloading Support

If we eventually leverage wolfcrypt's cryptography offloading to external devices such as Key Store,
Secure Element, HSM, PKCS 11, or TPM, this will violate some infallibility assumptions in certain
modules.

If this is enabled under some feature flag, these APIs will need to return Result types for the
circumstances in which these devices are not accessible.

Under this support, the API may change under this feature flag to retain stability of the common
path.

Regardless of the direction taken, undefined behavior from potential errors introduced from this
feature is completely unacceptable.

* Acceleration

** IMXRT1170 MCUs

Currently, for the SHA2 family of hash functions, it is not confirmed that enabling the
NXP CAAM proprietary acceleration will cause the associated functions to be fallible under
our configuration.
Confirming this, and acting accordingly is a requirement.

** PIC32MZ MCUs

This follows the same guidelines as IMXRT1170 MCUs (of course, this does not include NXP CAAM).
